I manually scanned the full 90-id listing for duplicates, unlike recent audits where I
took a clean count at face value. **Found one: `t-contacts-restate-0725` appears twice**,
at lines 28 and 72:

- **Line 28's copy:** `status: "done"`, carries a `CLOSED 2026-07-26 (Hemera, standup)`
  addendum explaining the closure (work was done 07-25, status never flipped).
- **Line 72's copy:** `status: "backlog"`, the original 07-25 entry, word-for-word
  identical `title`/`owner`/`createdAt`/`due`/`links` and near-identical `notes` (missing
  only the closure addendum) — untouched.

This is not the counting-tool artifact this pipeline has chased on 07-20/07-21/07-22/07-25
(that was always a single real entry miscounted by a flaky grep mode). This is a second,
literal copy of the same task id sitting in the file, one edited to `done`, one left at
`backlog`. It happened as a direct side effect of today's own housekeeping: Hemera's
turn describes "closing" `t-contacts-restate-0725` — the correct action would have been
editing the sole existing entry in place; what actually happened is a new entry was
appended with the closure note while the original was left standing. This is the exact
task-status-flip-lag failure mode I flagged yesterday (`t-task-status-flip-lag-pattern`)
recurring in a new shape: not lag this time, but duplication introduced while trying to
fix lag.

**Consequence:** low in this instance — both copies carry identical, accurate facts about
the 10k.emraan restate, so nothing false is asserted twice. But it is a real schema
integrity break (README's contract implies one entry per id; the dashboard or any
consumer keying off `t-contacts-restate-0725` would get an ambiguous result depending on
which one it reads), and it is worse in kind than a miscounted grep because it will not
self-correct on the next clean recount — it needs an actual fix.

**Filed:** `t-tasks-json-duplicate-id-contacts-restate-0725` (owner: mnemosyne, since she
